# البنية التقنية — MK Finance

## 1. المنصة والتقنيات
- Android Native باستخدام Kotlin.
- Jetpack Compose وMaterial 3 للواجهة.
- Room للتخزين المحلي.
- ViewModel وStateFlow لإدارة حالة الشاشة.
- Coroutines للعمليات غير المتزامنة.
- WorkManager للتذكيرات والمهام المؤجلة عند الحاجة.
- GitHub Actions للاختبارات وبناء APK.

الإصدارات الفعلية للأدوات والمكتبات تُؤخذ من ملفات Gradle في الفرع، ولا تُحدّث هنا إلا بعد تغييرها والتحقق من البناء.

## 2. مبادئ المعمارية
- فصل واجهة المستخدم عن منطق الأعمال والتخزين.
- جعل الحسابات المالية حتمية وقابلة للاختبار.
- استخدام Repository للوصول إلى البيانات.
- عدم وضع قواعد المحاسبة داخل Composable.
- إدارة عمليات الكتابة ضمن معاملات قاعدة بيانات عند الحاجة لضمان الاتساق.
- ترحيلات Room صريحة ومختبرة، وعدم استخدام destructive migration لبيانات مالية حقيقية. أُضيفت ترحيلات 2→3 للمحافظ والتحويلات، و3→4 للتصنيفات، و4→5 لتفرد أسماء التصنيفات، و5→6 للميزانيات الشهرية، و6→7 للديون، و7→8 لأهداف الادخار، و8→9 للرواتب والدخل المتكرر، و9→10 للمصروفات المتكررة. يلزم اختبار سلسلة الترحيل كاملة على قواعد فعلية قبل الإصدار.

## 3. الطبقات المقترحة
- **Presentation:** الشاشات، مكونات Compose، ViewModels وحالة الواجهة.
- **Domain:** حالات الاستخدام، قواعد الحساب، التحقق من المدخلات ونماذج النوايا.
- **Data:** Room entities/DAO/database، المستودعات ومصادر البيانات.
- **Voice:** واجهة Speech Recognition، تطبيع النص، محلل النوايا ومراجعة الأمر.
- **Core:** تنسيق المبالغ والعملات والتواريخ والنتائج والأخطاء.

هذه هي البنية المستهدفة؛ لا يُفترض أن جميع الطبقات منفذة حالياً. تُسجل الفجوات في ROADMAP.

## 4. نموذج البيانات المفاهيمي
الكيانات المتوقعة مع تطور المنتج:
- **منفذ مبدئياً في Room v3:** Wallet (الاسم والنوع والعملة والرصيد الافتتاحي)، Transaction (النوع والمبلغ والعملة والمحفظة والتصنيف والتاريخ والوصف)، وTransfer (المحفظة المصدر والوجهة والمبلغ والعملة والملاحظة).
- **مخطط:** Category قابلة للتخصيص، وحالة المحفظة وأرشفتها، وExchangeRate بمصدر وتاريخ صلاحية.
- Budget: الفترة والحد والتصنيف/النطاق.
- Debt: الطرف والاتجاه والمبلغ الأصلي والمتبقي والحالة.
- DebtPayment: دفعة مرتبطة بدين وتاريخها.
- SavingsGoal: الهدف والمبلغ المستهدف والتاريخ والحالة.
- SavingsEntry: مساهمة أو سحب مرتبط بهدف.
- RecurringRule: التكرار وتاريخ الاستحقاق والقيمة والإعدادات.
- Reminder: وقت التنبيه ونوعه وحالته.
- ExchangeRate: العملتان والسعر ومصدره وتاريخ تحديثه.

لا يلزم تنفيذ كل الكيانات في المرحلة الأولى. يجب تصميم العلاقات والمفاتيح والترحيلات قبل إدخال كل مجموعة.

## 5. الدقة المالية
- لا تستخدم Float أو Double لتخزين المبالغ المالية.
- استخدم تمثيلاً صحيحاً ثابت الدقة (مثل وحدات العملة الصغرى أو قيمة عشرية ممثلة بأعداد صحيحة) مع تحديد دقة كل عملة.
- لكل محفظة رصيد مستقل بعملتها؛ لا تجمع العملات المختلفة في رقم إجمالي واحد.
- يدعم الإصدار الأول من واجهة المحافظ YER وUSD وSAR وAED، مع دقة تخزين ثابتة من منزلتين عشريتين.
- التحويلات الحالية مسموحة بين محافظ العملة نفسها فقط، وتُخزن في جدول مستقل فلا تدخل في إجمالي الدخل أو المصروف.
- لا يوجد تحويل عملات أو سعر صرف آلي حتى الآن؛ يجب توفير سعر موثق وتاريخ ومصدر قبل السماح بالتحويل بين عملتين.
- اختبر الحدود والتقريب والتحويلات والسداد الجزئي.
- اجعل العمليات المترابطة ذرية لمنع نصف تحويل أو نصف سداد.
- لا تحتسب التحويل الداخلي كدخل أو مصروف.

## 6. العمل دون اتصال
- تخزين وعرض العمليات والأرصدة والتقارير الأساسية محلياً.
- لا يتطلب إنشاء معاملة أو حساب الرصيد خادماً.
- التعرف الصوتي عبر Vosk داخل التطبيق بعد استيراد نموذج عربي محلي؛ لا رجوع سحابي أو خدمة نظام. الإدخال اليدوي يظل مستقلاً عن النموذج.
- لا توجد مزامنة سحابية في النطاق الأول.

## 7. الأمان والخصوصية
- طلب صلاحية الميكروفون وقت الحاجة فقط.
- عدم تسجيل الصوت في الخلفية.
- عدم كتابة بيانات مالية حساسة في Logcat أو تقارير الأعطال.
- تشفير النسخ الاحتياطية وحماية مفاتيحها باستخدام آليات Android المناسبة.
- توضيح حدود الحماية المحلية وإمكانية فقد البيانات عند حذف التطبيق إذا لم توجد نسخة احتياطية.

## 8. الاختبارات
- Unit tests للحسابات والمبالغ والتواريخ ومحلل الصوت.
- Database tests للعلاقات والترحيلات والعمليات الذرية.
- UI tests للتنقل وRTL والتأكيد والإلغاء وحالات الخطأ.
- اختبارات على API 23 وما فوق بقدر توفر بيئة الاختبار.
- CI يجب أن يشغل الاختبارات ثم assembleDebug، وألا يرفع APK إلا عند نجاح البناء.

## 9. قواعد التغيير
- راجع تأثير أي تعديل على البيانات المحفوظة والترحيلات.
- لا تغيّر schema دون migration واختبار.
- لا تضف خدمة خارجية دون مراجعة الخصوصية والاتصال.
- وثّق القرارات المعمارية المهمة في DECISIONS.md.


## 10. التصنيفات (Room v5)
- التصنيف كيان مستقل في جدول categories، والاسم فريد بغض النظر عن النوع لتجنب ظهور تصنيفين بالاسم نفسه في قوائم الاختيار.
- الأنواع المسموحة: INCOME وEXPENSE وBOTH.
- الأرشفة تغيّر isActive فقط؛ لا تحذف التصنيف ولا تغيّر نصوص التصنيفات المحفوظة على العمليات السابقة.
- يمكن إعادة تفعيل التصنيف المؤرشف. لا يُعاد استخدام الاسم بإنشاء سجل مكرر حتى عند اختلاف النوع.
- ترحيل 3→4 ينشئ الجدول ويزرع التصنيفات الافتراضية دون تعديل جدول transactions. ترحيل 4→5 يدمج الأسماء المكررة غير الحساسة لحالة الأحرف، ثم يفرض تفرد الاسم.
- واجهة الصوت والتعديل تعرض التصنيفات النشطة المتوافقة مع نوع العملية.
- اختبار الترحيل على ملف قاعدة بيانات v3 حقيقي مطلوب قبل إصدار التطبيق.


## 11. الميزانيات الشهرية (Room v6)
- لكل ميزانية تصنيف مصروف وعملة ومفتاح شهر ثابت بصيغة YYYY-MM وحد أعلى بوحدات العملة الصغرى.
- لا تجمع الميزانية إنفاق عملتين مختلفتين، ولا تحتسب الدخل أو التحويلات الداخلية.
- فترة الإنفاق تحسب من بداية الشهر المحلي إلى بداية الشهر التالي، بينما مفتاح YYYY-MM يحافظ على هوية الميزانية عند تغيير المنطقة الزمنية للجهاز.
- التحذير داخل التطبيق عند بلوغ 80%، وتظهر حالة تجاوز الحد عند الوصول إلى 100% أو أكثر.
- لا توجد إشعارات نظامية بالخلفية في هذه الدفعة.
- ترحيل 5→6 ينشئ جدول budgets وفهرساً فريداً يمنع ميزانيتين للتصنيف/العملة/الشهر نفسه.


## 12. الديون والسلف (Room v7)
- FinanceDebt يحفظ الطرف، الوصف، نوع الالتزام (OWED_BY_ME أو OWED_TO_ME)، أصل المبلغ، العملة والمحفظة المرجعية، وما إذا كان أصل الدين قد حُرّك نقدياً. عند تسجيل دين قديم يمكن تعطيل حركة الأصل لتجنب تكرارها.
- FinanceDebtPayment يسجل كل دفعة مستقلة ويربطها بمعاملة مالية واحدة عبر transactionId فريد.
- تسجيل أصل قرض مستلم يولّد حركة DEBT_RECEIVED تزيد النقدية، وتسجيل سلفة ممنوحة يولّد DEBT_ISSUED تنقص النقدية؛ كلاهما لا يدخل في إجماليات الدخل/المصروف التشغيلية.
- إنشاء الدين يولّد حركة أصل منفصلة عن الدخل/المصروف: DEBT_RECEIVED يزيد رصيد المحفظة عند استلام قرض، وDEBT_ISSUED يخفضه عند إقراض سلفة. السداد يولّد EXPENSE والتحصيل يولّد INCOME.
- إنشاء الدين وحركة أصل القرض/السلفة تتم داخل Room transaction واحدة. كما تتم إضافة الدفعة وحركة دفتر الأستاذ داخل معاملة واحدة؛ ويُعاد قراءة الرصيد والدفعات داخل المعاملة لمنع تجاوز المتبقي أو السحب فوق الرصيد مع الطلبات المتزامنة.
- الحسابات تستخدم BigInteger، ولا يسمح بمبلغ دفعة موجب أكبر من الرصيد المستحق.
- ترحيل 6→7 يضيف debtId اختيارياً إلى transactions وينشئ جدولي debts وdebt_payments وفهارسهما دون تعديل العمليات القديمة.
- لا يوجد حالياً تعديل أصل الدين أو حذفه أو نقل الدين إلى محفظة أخرى؛ تُحفظ الدفعات كسجل تدقيق.


## 13. أهداف الادخار والمساهمات (Room v8)
- FinanceSavingsGoal يحفظ اسم الهدف، المبلغ المستهدف بوحدات العملة الصغرى، العملة، والمحفظة المرتبطة به.
- FinanceSavingsEntry يسجل كل مساهمة أو سحب كحدث مستقل ويربطه بمعاملة دفتر أستاذ واحدة عبر transactionId فريد.
- المساهمة تنشئ حركة SAVINGS_CONTRIBUTION فتقلل الرصيد المتاح في المحفظة، لكنها ليست مصروفاً تشغيلياً ولا تدخل في إجمالي المصروفات.
- السحب ينشئ حركة SAVINGS_WITHDRAWAL فتزيد الرصيد المتاح في المحفظة، لكنه ليس دخلاً تشغيلياً ولا يدخل في إجمالي الدخل.
- إنشاء الهدف لا يحرك النقدية. العملة ثابتة وموروثة من المحفظة المرتبطة؛ لا تُجمع أرصدة أهداف بعملات مختلفة.
- تُنفذ المساهمة والسحب ضمن Room transaction واحدة مع سجل الادخار وحركة دفتر الأستاذ. يعاد قراءة الهدف والسجل والمحفظة والرصيد داخل المعاملة لمنع تجاوز الهدف أو سحب أكثر من المدخر.
- لا يسمح بتعديل أو حذف حركات الادخار من سجل العمليات العام؛ تتم إدارتها من قسم الادخار للحفاظ على تطابق دفتر الأستاذ مع سجل المساهمات والسحوبات.
- ترحيل 7→8 يضيف savingsGoalId اختيارياً إلى transactions وينشئ savings_goals وsavings_entries وفهارسها دون تعديل السجلات القديمة.


## 14. الرواتب والدخل المتكرر (Room v9)
- FinanceRecurringIncomeRule يحفظ اسم المصدر، نوعه (راتب/دخل متكرر)، المبلغ، العملة، المحفظة، التكرار (أسبوعي/شهري)، يوم الاستحقاق الشهري، وتاريخ الاستحقاق التالي وحالة التفعيل.
- FinanceRecurringIncomeEntry يسجل كل استحقاق تم تأكيد استلامه، ويربطه بمعاملة دخل واحدة. يوجد قيد فريد على (ruleId, occurrenceKey) وقيد فريد على transactionId لمنع تكرار تسجيل الفترة نفسها.
- لا تُنشأ معاملات دخل تلقائياً عند حلول الموعد؛ يظهر الاستحقاق للمستخدم ويجب عليه تأكيد الاستلام يدوياً. هذا يمنع تضخيم الدخل بسبب راتب متوقع لم يصل فعلياً.
- تأكيد الاستحقاق ينشئ معاملة INCOME مرتبطة بالمحفظة والقاعدة، ثم سجل الاستحقاق، ثم يحرك الموعد التالي، وكل ذلك داخل db.withTransaction واحدة. أي فشل يتراجع عن جميع التغييرات.
- التكرار الشهري يحافظ على يوم الاستحقاق الأصلي، ويقص اليوم إلى آخر يوم في الشهر القصير ثم يعود إلى اليوم الأصلي في الشهر التالي. التكرار الأسبوعي يضيف سبعة أيام تقويمية.
- الاستحقاقات المتأخرة لا تُسجل دفعة واحدة؛ كل فترة تحتاج تأكيداً مستقلاً، ويمكن إيقاف القاعدة وإعادة تفعيلها دون فقد تاريخها.
- حركات الدخل المرتبطة بقاعدة دورية لا يمكن تعديلها أو حذفها من سجل العمليات العام؛ هذا يحافظ على التطابق بين دفتر الأستاذ وسجل الاستحقاقات.
- يسمح محرر القاعدة بتغيير الاسم والمبلغ فقط. تبقى المحفظة والعملة ونوع الدخل والتكرار ويوم الارتكاز والموعد الحالي ثابتة، وتظل مبالغ المعاملات السابقة محفوظة كما سُجلت.
- ترحيل 8→9 يضيف recurringIncomeRuleId اختيارياً إلى transactions وينشئ recurring_income_rules وrecurring_income_entries وفهارس التفرد، دون تعديل العمليات القديمة.
- لا يرسل هذا الإصدار إشعارات تلقائية للرواتب؛ متابعة الاستحقاق تتم داخل قسم الرواتب، بينما تذكيرات الفواتير منفذة عبر WorkManager.


## 15. المصروفات المتكررة (Room v10)
- FinanceRecurringExpenseRule يحفظ اسم الالتزام، تصنيف المصروف، المبلغ، العملة، المحفظة، التكرار الأسبوعي/الشهري، يوم الاستحقاق، الموعد القادم وحالة التفعيل.
- FinanceRecurringExpenseEntry يسجل كل دفعة مؤكدة ويربطها بمعاملة EXPENSE واحدة. قيد فريد على (ruleId, occurrenceKey) وقيد فريد على transactionId يمنعان تكرار تسجيل الفترة أو ربط المعاملة مرتين.
- لا تُنشأ المصروفات تلقائياً عند حلول الموعد. يجب على المستخدم تأكيد الدفع؛ لذلك لا يُخصم مبلغ لمجرد أن موعد الإيجار أو الفاتورة حلّ.
- تأكيد الدفع والتحقق من المحفظة والعملة والرصيد الحالي وإنشاء حركة EXPENSE وسجل الدفعة وتحديث الموعد التالي تتم داخل db.withTransaction واحدة.
- عند عدم كفاية الرصيد، أو كون الموعد غير مستحق، أو تسجيل الفترة سابقاً، تُلغى العملية كلها ولا يتغير الرصيد.
- حركات المصروفات المرتبطة بقاعدة دورية محمية من التعديل والحذف عبر سجل العمليات العام حفاظاً على سجل التدقيق.
- ترحيل 9→10 يضيف recurringExpenseRuleId اختيارياً إلى transactions وينشئ recurring_expense_rules وrecurring_expense_entries وفهارس التفرد، دون تعديل السجلات السابقة.
- لا توجد بعد إشعارات خلفية للمواعيد؛ تظهر الاستحقاقات داخل قسم مالي عند فتح التطبيق.


## 16. الفواتير والاستحقاقات (Room v12)
- FinanceBill يحفظ اسم الفاتورة وتصنيفها ومبلغها وعملتها ومحفظة الدفع وتاريخ الاستحقاق التالي ونوع التكرار (مرة واحدة/شهري/سنوي).
- FinanceBillPayment يسجل كل دفعة مؤكدة ويربطها بمعاملة EXPENSE واحدة. يوجد قيد فريد على (billId, occurrenceKey) وقيد فريد على transactionId لمنع تكرار الفترة أو ربط المعاملة مرتين.
- لا يؤدي حلول موعد الفاتورة إلى إنشاء حركة أو خصم تلقائي. تعرض الشاشة حالة قادمة/مستحقة، ولا يُسجل المصروف إلا بضغط المستخدم على تأكيد الدفع.
- تأكيد الدفع يعيد قراءة الفاتورة والمحفظة والعمليات والتحويلات داخل db.withTransaction، ويتحقق من حلول الموعد وتطابق العملة وكفاية الرصيد، ثم ينشئ EXPENSE وسجل الدفع ويحدّث الموعد التالي أو يغلق الفاتورة ذات الاستحقاق الواحد.
- فشل أي خطوة يتراجع عن المعاملة كلها. حركات الفواتير المرتبطة لا يمكن تعديلها أو حذفها من سجل العمليات العام.
- التكرار الشهري والسنوي يحافظ على يوم/شهر الارتكاز عند الأشهر القصيرة والسنوات الكبيسة. كل دورة متأخرة تحتاج تأكيداً مستقلاً؛ لا تُسجل الدورات المتراكمة تلقائياً.
- ترحيل 10→11 يضيف billId اختيارياً إلى transactions وينشئ bills وbill_payments وفهارس التفرد دون تعديل البيانات المالية السابقة.
- ترحيل 11→12 يضيف lastReminderOccurrenceKey الاختياري إلى bills. يسجل عامل WorkManager مفتاح دورة الفاتورة بعد إرسال الإشعار، ويمنع إعادة إرسال تذكير الدورة نفسها عند فتح التطبيق أو إعادة مزامنة الأعمال؛ يتغير المفتاح تلقائياً مع دورة الاستحقاق التالية.
- تعرض الشاشة حالة الفاتورة داخل التطبيق، كما تُجدول إشعارات محلية عبر WorkManager قبل الاستحقاق بنحو 24 ساعة (أو فوراً إذا كان الموعد أقرب). يتحقق العامل من أن الفاتورة ما زالت نشطة وأن الموعد لم يتغير قبل إرسال الإشعار، ويُلغى/يعاد جدولة العمل عند الإيقاف أو الدفع أو التعديل. على Android 13+ يلزم منح POST_NOTIFICATIONS؛ وإذا رُفض الإذن تبقى حالة الاستحقاق ظاهرة داخل التطبيق.


## 17. فهم الأوامر الصوتية والاستعلامات
- VoiceRecognitionIntentFactory وSpeechRoutePolicy يختاران نشاط ACTION_RECOGNIZE_SPEECH الافتراضي بـar-YE عند توفر handler، بما يشمل Android6–11. SystemSpeechController مخصص لـon-device الاختياري على API31+ عند توفره. PREFER_OFFLINE ليس ضمان عدم اتصال المزود. لا Vosk/JNA أو نماذج؛ يستهدف الإصلاح APK أقل من 30 MB ويقيس ملفه بعد البناء.
- VoiceTransactionParser مستقل ونقي ولا يتصل بقاعدة البيانات أو الشبكة؛ يطبع الأرقام العربية والفارسية واللاتينية ويحلل عدداً من الصيغ المنطوقة الشائعة.
- VoiceCommandType يميز استعلام الرصيد والدخل والمصروف والملخص عن أوامر إنشاء المعاملات حتى لا يتحول السؤال إلى حركة مالية.
- VoiceQueryEngine يحسب إجماليات محلية باستخدام BigInteger ويفصل المحفظة والعملة والفترة.
- شاشة المساعد تعرض المسودة للتعديل وتسمح بإلغائها، ولا تحفظ إلا بعد تأكيد المستخدم. زر الحفظ محمي من النقر المتكرر.
- نطاق فهم اللهجة اليمنية الحالي مجموعة أولية قابلة للتوسعة، ولا يعني ضمان فهم كل اللهجات أو توفر التعرف الصوتي دون اتصال.

## 18. التقارير والتصدير
- FinanceReportAnalytics يجمع الدخل والمصروف في فترات يومية/أسبوعية/شهرية/سنوية، ويفصل المحفظة والعملة.
- تفصيل التصنيفات يحسب المصروفات الإيجابية فقط ضمن الفترة الحالية.
- FinanceReportExporter ينتج CSV بترميز UTF-8، وXLSX بسيطاً متوافقاً مع OpenXML، وPDF باستخدام دعم Android الأصلي مع اتجاه RTL.
- لا تجمع التقارير محافظ بعملات مختلفة في رقم واحد؛ يختار المستخدم المحفظة أولاً.
- CSV يحيّد بادئات الخلايا التي قد تفسر كصيغ عند فتح الملف في برامج الجداول.

## 19. النسخ الاحتياطي والاستعادة
- FinanceBackupManager يصدّر جداول Room المحددة إلى JSON داخلي ثم يشفره باستخدام AES-256-GCM، مع salt وnonce عشوائيين وPBKDF2-HMAC-SHA1 بعدد 310,000 دورة لتوافق Android 6+.
- كلمة المرور لا تُحفظ في التطبيق، ويُطلب من المستخدم إدخالها عند النسخ والاستعادة.
- الاستعادة لا تبدأ قبل فك التشفير والتحقق من الترويسة وإصدار المخطط ووجود الجداول، ثم تنفذ حذف/إدخال البيانات داخل Room transaction واحدة؛ أي فشل يعيد الحالة السابقة.
- الإصدار الأول يقبل نسخ Room schema v12 فقط؛ لا يدعي توافق النسخ بين مخططات مختلفة.
- حجم ملف النسخ محدود بـ64 MiB لحماية الذاكرة، وAndroid Auto Backup معطل لتجنب رفع قاعدة مالية غير مشفرة عبر النسخ النظامي.


## 20. التواريخ النسبية في الإدخال الصوتي
- يقرأ المحلل اليوم وأمس وأول أمس كتاريخ للحركة، ويحوّلها إلى createdAt محلياً باستخدام Calendar ومنطقة زمنية الجهاز.
- إذا لم يذكر المستخدم تاريخاً، يستخدم وقت الإدخال الحالي. لا يخمن المحلل تاريخاً مطلقاً من دون عبارة واضحة.


## 21. توقيع إصدار Android
- إعداد Gradle يفعّل signingConfig للإصدار فقط عندما تتوفر متغيرات البيئة الأربعة الخاصة بمسار keystore وكلمة مروره واسم المفتاح وكلمة مرور المفتاح.
- GitHub Actions ينشئ ملف keystore مؤقتاً في مساحة runner من Secret Base64 ثم يبني Release ويرفعه فقط عند وجود جميع الأسرار.
- لا تحفظ ملفات keystore أو كلمات المرور في Git، ولا يمكن إنتاج إصدار موقع نهائي قبل أن يضيف مالك التطبيق أسراره الخاصة.

## 22. تقليل بقاء بيانات النسخ في الذاكرة
- عند التصدير تُمسح مصفوفة JSON الصريحة ومخازن salt/nonce/ciphertext المؤقتة بعد كتابة النسخة، وعند الاستعادة تُمسح مصفوفة النص المفكوك وبيانات الملف المؤقتة بعد انتهاء العملية.

## 22. معاينة التصميم المنفصلة
- `web-preview/` تطبيق Vite/JavaScript/CSS مستقل، وليس Kotlin/Compose Multiplatform ولا WebView يشغل APK.
