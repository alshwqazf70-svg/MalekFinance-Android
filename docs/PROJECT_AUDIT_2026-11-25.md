### ملاحظتان على السلوك الجديد

1. رفض مبلغ ملتبس أفضل من اقتراح مبلغ خاطئ؛ لم يُضف دعم عام لفواصل الآلاف أو مزج الأرقام والكلمات إلى محلل الصوت. بعض العبارات التي كانت تعطي رقماً تخمينياً تحتاج الآن إدخالاً يدوياً واضحاً.
2. المبالغ الكبيرة المحفوظة كنص في Excel لا تدخل تلقائياً في بعض دوال SUM. هذا مقصود لحفظ الدقة. CSV يبقى نصاً رقمياً دقيقاً داخل الملف، لكن فتحه آلياً في Excel قد يعيد تفسير الأرقام؛ اختر استيراد العمود كنص أو استخدم XLSX المحسّن.

## 3. النتائج المتبقية — لم تُحل كلها

### أولوية أولى قبل الاعتماد المالي/الإصدار

**R1 — تحقق Android الفعلي غير متوفر.**
- لا Gradle wrapper ولا Android SDK/Gradle مثبت في بيئة الجلسة، ومصادر تنزيل Android/Maven ليست ضمن الوصول الشبكي المتاح.
- لم تُختبر Compose أو KSP أو Room generated code أو Android lint فعلياً هنا. التحليل النحوي ومشغّل JVM لا يثبتان أن APK يُبنى.
- المطلوب: تشغيل CI على نفس التغييرات، نجاح unit/lint/assembleDebug/assembleDebugAndroidTest/connectedDebugAndroidTest، ثم تجربة جهاز.
- إضافة Gradle wrapper موثق الإصدار والتحقق من checksum تحسن إعادة إنتاج البناء محلياً؛ لا تنزّل Wrapper JAR عشوائياً.

**R2 — التحقق الدلالي لاستعادة النسخة الاحتياطية غير كافٍ.**
- `FinanceBackupManager.restore` يتحقق من AES-GCM وصيغة النسخة v12 وأسماء الأعمدة وينفذ الإدخال داخل transaction؛ هذه نقاط جيدة.
- لكن Entities لا تحتوي ForeignKey/CHECK لحماية جميع العلاقات، والاستعادة لا تتحقق بشكل شامل من wallet/debt/payment/transaction والعملة/النوع/المبلغ لكل سجل.
- لذلك ملف **صحيح التشفير ومعروف كلمة المرور لكنه مُنشأ بمنطق خاطئ** قد يمر شكلياً ويحمل سجلات يتيمة أو متناقضة. هذا ليس ادعاء أن شخصاً يستطيع تجاوز AES-GCM دون كلمة المرور.
- المطلوب: مرحلة تحقق دلالي قبل اعتماد الاستعادة، واختبارات رفض السجلات اليتيمة، اختلاف العملات، الدفعات المتجاوزة، وروابط المعاملات غير المتطابقة. قيود قاعدة البيانات تحتاج migration مدروساً، لا إضافتها عشوائياً فوق بيانات المستخدم.

**R3 — سلامة مكتبات الصوت الأصلية لم تعتمد على جهاز.**
- Vosk/JNA يحتاجان اختبار ABI وAndroid 6/API23 وأجهزة حديثة و16KB memory pages والذاكرة وتكرار البدء/الإيقاف.
- لا نموذج عربي مرفق، ولا ضمان لدقة اللهجة اليمنية، ولا تنزيل/تدريب نموذج داخل هذه المراجعة.
- تثبيت ZIP محدود بالمساحة والحجم وعدد الملفات وبمسار آمن، لكنه ليس تحققاً من أصالة المورد. استخدم نموذجاً موثوقاً وراجع رخصته.

### أولوية ثانية — موثوقية وأداء وسلامة الاستخدام

**R4 — الواجهة كبيرة ومنطق الكتابة موزع.**
- `FinanceApp.kt` يتجاوز 2200 سطر، ويحتوي التحليل والعرض وبعض الكتابة والتحقق والتصدير معاً. الرواتب والمصروفات المتكررة لا تزال تنفذ معاملات في composables مباشرة.
- خطر الصيانة: اختلاف التحقق بين المسارات اليدوية والصوتية، وصعوبة اختبار دورة الحياة.
- المطلوب: ViewModels/حالات شاشة وخدمات أوامر مشتركة؛ فصل التعديل والحذف والإنشاء مثل خدمات السداد والتحويل الحالية. نقل تدريجي مع اختبارات، لا إعادة كتابة غير مختبرة.

**R5 — المسودات وعمليات UI تحتاج اختبار دوران/خروج/إلغاء.**
- كثير من المدخلات تستخدم `remember` لا `rememberSaveable` أو SavedStateHandle، فتفقد المسودة عند إعادة إنشاء Activity.
- `runCatching` واسع في عدة coroutines قد يبتلع CancellationException؛ بعض العمليات قد تكتمل دون أن تصل رسالة نجاح للشاشة بعد مغادرتها.
- المطلوب: سياسات واضحة للاحتفاظ بالمسودات ومنع التكرار، وفصل عمر عملية الحفظ عن composable، واختبارات rotation/background/process recreation، مع إعادة رمي cancellation حيث يلزم.

**R6 — عمر اتصال Room في MainActivity.**
- تُنشأ قاعدة جديدة في `onCreate` دون singleton مركزي أو إدارة إغلاق مقابلة. إعادة إنشاء Activity قد تنشئ مثيلات ومسابح تنفيذ غير لازمة.
- المطلوب: مزود قاعدة على مستوى applicationContext، مع سياسة واضحة لاتصالات العمال والاختبارات. لا تغلق قاعدة مشتركة وهي ما زالت مستخدمة.

**R7 — حد النسخة الاحتياطية يأتي بعد بناء JSON كاملاً.**
- حد 64 MiB لا يمنع استهلاك ذاكرة كبير قبل الوصول إلى الفحص؛ توجد JSONArray/JSONObject ثم String وByteArray وciphertext في الذاكرة.
- المطلوب: اختبار حجم واقعي على جهاز منخفض الذاكرة، وحدود مبكرة/كتابة متدفقة أو تنسيق مرحلي مشفر. لا تعتمد على حد الملف وحده لمنع OOM.

**R8 — تغير الشهر/التوقيت أثناء بقاء الشاشة مفتوحة.**
- `MoneyScreen` يحتفظ بـ`budgetMonth` داخل `remember` دون مفتاح زمني؛ قد يبقى شهر سابق إذا عبر المستخدم إلى شهر جديد دون إعادة دخول الشاشة.
- التقرير والاستعلامات وبعض التجميعات تعتمد توقيت الجهاز، بينما كشف الشخص بتوقيت عدن. هذا ليس تلف timestamp، لكنه اختلاف يجب توضيحه للمستخدم.
- المطلوب: تحديث clock عند العودة للشاشة وعند تغير اليوم/الشهر، وتحديد سياسة timezone متسقة، واختبار الحدود الزمنية.

**R9 — حذف العمليات العادية فوري.**
- معاملات الديون/الادخار/الفواتير المرتبطة محمية من الحذف العام في الواجهة، وهذا صحيح، لكن حذف العملية العادية لا يطلب تأكيداً أو يوفر تراجعاً.
- المطلوب: تأكيد واضح أو Undo وسجل مراجعة حسب متطلبات المنتج. قرار السماح برصيد سلبي للمصروف اليدوي يجب توثيقه؛ ليس كل تسجيل مصروف تاريخي غير ممول خطأ بالضرورة.

**R10 — نمو البيانات والأداء.**
- كثير من الشاشات تراقب كل الجداول وتجمع كل السجلات في الذاكرة؛ البحث/الفلاتر وبعض التجميعات تتكرر مع recomposition. كشف الحساب وتخصيصاته يحتويان عمليات filtering متداخلة.
- المطلوب: قياس 10 آلاف/100 ألف سجل، queries مجمعة ومفهرسة، Paging عند الحاجة، و`collectAsStateWithLifecycle` بدلاً من جمع غير مرتبط بدورة الحياة، واختبارات تكبير الخط/RTL/الوصول.

### أولوية ثالثة — تحسينات وحماية إضافية

- تطبيق Android لا يقدم حالياً قفل PIN/بصمة أو تشفيراً مستقلاً لقاعدة Room؛ البيانات داخل sandbox الجهاز، والنسخة المشفرة ليست هي تشفير القاعدة نفسها. قرر threat model قبل إضافة هذه الميزات.
- إشعارات الفواتير قد تعرض عنوان الفاتورة على شاشة القفل؛ يفضل إعداد خصوصية للمحتوى.
- وضع الخصوصية في Android موصوف بأنه لإخفاء **مبالغ الرئيسية**، وليس قفلاً شاملاً للتطبيق.
- `exportSchema=false`: حفظ Room schema JSON بإصداراته سيسهّل التدقيق واختبار migrations. فحص SQL أدناه لا يحل محل Room schema validation.
- الويب معاينة ببيانات localStorage غير مشفرة، لا دفتر مالي إنتاجي. فتح تبويبين قد يؤدي إلى آخر كتابة تكسب؛ لا مزامنة/كشف تنازع أو نسخ احتياطي مالي فيه.
- لا تستخدم نجاح `npm audit` كحكم على أمن Android أو مكتبات `.so` أو على خلو التبعيات من ثغرات غير منشورة.
- فحص أسرار محدود لم يجد مرشحين لأنماط private keys/GitHub tokens/AWS access keys في المصدر المحدد؛ ليس تدقيقاً لتاريخ Git ولا ضمان عدم وجود أسرار بصيغ أخرى.

اختبارات PDF الطويل وRoom/Compose/backup instrumentation موجودة في المصدر ولكن **لم تُنفذ**. لم يُنشأ APK في هذه الجلسة. تغييرات خيط التصدير وPDF ومسح كلمة المرور تحتاج أيضاً تحقق Android مناسباً.

## 5. أدوات إعادة الفحص

```bash
# يحتاج توزيعة Kotlin/JDK محلية؛ لا يقوم بتنزيلها
KOTLINC=/path/to/kotlinc JAVA_HOME=/path/to/jdk python3 scripts/audit-core.py
python3 scripts/audit-migrations.py

cd web-preview
npm ci
npm test
npm audit
npm run export:bundle
npx playwright install chromium
npm run test:e2e
```

`audit-core.py` يستخدم ملفات المنطق والاختبارات الأصلية مع assertion shim، ويستبعد Android PDF من نسخة تصدير مؤقتة؛ اختبارات CSV/XLSX تبقى على كودها نفسه. لا تستخدم نتيجة المشغّل بديلاً عن أوامر Gradle الرسمية.

في بيئة Android الكاملة: اتبع workflow وشغّل unit tests وlint وبناء التطبيق وAPK الاختبارات ثم connected tests. قبل الإصدار أضف جهاز API23 وجهازاً حديثاً واختبار الصوت/المشاركة/SAF والنسخ والاستعادة والأداء.

## 6. خطة العمل المقترحة

1. **اعتماد البناء أولاً:** نجاح Android CI على التغييرات الحالية، ومعالجة أي أخطاء compiler/lint/Room تظهر.
2. **سلامة البيانات:** تحقق دلالي للاستعادة واختبارات علاقات/عملات/مبالغ فاسدة، دون إتلاف البيانات الموجودة أو migrations مرتجلة.
3. **اعتماد الجهاز:** Vosk/ABI/16KB، PDF الطويل، فتح/حفظ الملفات، مشاركة كشف الشخص، ودوران/خروج أثناء الحفظ.
4. **رفع الموثوقية:** مزود Room موحد، ViewModels، حفظ المسودات، التأكيد/التراجع عن الحذف، وتحديث الشهر والتوقيت.
5. **الأداء والخصوصية:** أحجام كبيرة، تتبع دورة الحياة، الوصول وتكبير الخط، وقرار قفل التطبيق/إخفاء الإشعارات.

**الحكم النهائي:** تحسن المنطق القابل للاختبار وثبتت عدة أخطاء وأُصلحت. لا أوصي بتسمية الحالة الحالية «خالية من الأخطاء» أو الاعتماد عليها كنسخة مالية نهائية قبل إكمال بوابات التحقق أعلاه.

## متابعة التنفيذ بعد التقرير
